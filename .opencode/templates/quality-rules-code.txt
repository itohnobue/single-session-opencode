QUALITY RULES (CODE):
- Read every file BEFORE modifying it
- Every change MUST be minimal — only what task requires
- Follow existing code patterns and conventions
- Before adding code: Grep for existing similar functionality
- Do NOT expand scope beyond task
- Partial honest results > false completion — report actual completion %
- Cannot determine → "UNABLE TO DETERMINE", do NOT guess
- After completing a logical batch of edits (not after every single edit): run lint command
- Before calling a function/method: Read the source file to verify it exists with that exact signature
- Before reporting: re-read the task brief and compare every literal it names — public identifier, file path, CLI flag, config key, default value, error string — character-for-character against the delivered code, from the brief text, not from memory. A near-miss (renamed, recased, pluralized) is a defect, not a style choice. Where the repo's own convention conflicts with the brief's literal, the brief wins — follow it and report the conflict.
- Root cause first: investigate root cause before proposing workarounds (timeouts, retries, skip logic)
- Do NOT add error handling (try/catch, null checks, validation) for states the code cannot actually reach. Handle only reachable error paths — guarding impossible states is a common LLM-codegen anti-pattern that clutters code and masks real logic

Change-class obligations (state each under the report's `### Change Class` section; an applicable one left unanswered leaves the change unverified):
- Condition change (any change to a condition that decides whether a behaviour runs, retries, terminates or proceeds — a flag, predicate, threshold, budget, cursor, state check, permission check, lifecycle signal): state the BLOCK direction (which input states it still refuses, and that the harm the change targets is still covered) AND the LIVENESS direction (every input state in which it now refuses permanently, and why none of them is reachable while the guarded behaviour is expected to run). For a REMOVED condition the liveness half is vacuous (no input state refuses): state instead which harm the removal stops preventing, and why that harm cannot occur.
- Removing or neutering code whose comment, name, or history documents a specific past failure: state why that failure cannot recur under the new design. A comment left in place that now describes behaviour the code no longer has is a defect of this change.
- Changing when or whether a feature runs: name the feature's observable signal and the check that reads it. "It builds, the tests pass, the app launches" is not evidence for a behaviour change.

Mandatory test verification (skip = report auto-rejected by the main model):
- After ALL code changes are complete: run the targeted tests covering your change (the ENVIRONMENT section names the test command and how to select the tests covering a change). Never run the full suite — it is out of scope for this stage.
- Paste the ACTUAL test output (pass/fail counts, specific failures) into your report
- Do NOT write "all tests pass" without pasting the real output
- If test command is unavailable or fails to run: write "TESTS NOT RUN: [reason]"
- If some tests fail: list each failure with file:line and error message

FIX WITNESS (when this run implements a reviewed fix):
- Before editing, reproduce the original failure with the smallest targeted check; after the fix, re-run the same check. Paste both commands and their actual outputs — a described mechanism is not a witness.
- If no reproduction is possible, name a test that goes red when the fix is reverted and passes with it, or write `witness: not run — <why no reproduction is possible>`.
- For a static finding (a missing guard, a wrong predicate), the cited file:line is evidence of the defect but NOT a fix witness — state the witness form used or why none exists.

Check discipline (MANDATORY):
- A check counts as passed only if you ran it during THIS task. Otherwise report it as not run.
- Run the check the task names, at the scale it names. A narrower or faster substitute (one test file for the suite, a build instead of the tests) is reported as what it is — never as the named check — with the exact command you ran.
- A check that exists in the repo and was skipped is UNVERIFIED work, not a "could not check" item.
- Assert on CONTENT, not shape or count: "the command printed PASS" is not evidence that the asserted value matched — read the value the check produced.
- A count is evidence of ABSENCE at scale, never of correctness. Distinguish "I found N" (a count) from "I saw N" (a display): a listing read through a truncating display is not a count — count with `grep -c` / `grep -o`, or read the full output.
- When re-checking a completeness inventory, use a DIFFERENT method than the one that built it — re-running the same check reproduces the same blind spot.

TEST QUALITY (when you write or update a test):
- NEVER assert on mock behavior — test what the code does, not what the mocks do
- NEVER add test-only methods to production code
- NEVER mock a dependency you do not understand — understand it first
- If mock setup is more than half the test, the test is testing the mocks: restructure it
- NEVER delete or weaken production code to make a test pass. If no failing baseline exists, state that limit instead of calling the change verified

Anti-shortcut thoughts (slow down if any of these appear in your reasoning):
- "This is probably fine without testing" → run the test command, paste the actual output
- "The error looks flaky, I'll retry and move on" → investigate the cause; flakiness hides real bugs
- "I'll suppress the warning/error to get it passing" → suppression is not a fix; find the root cause first
- "I'll relax the check's config to get it passing" → a check's configuration is not the defect; fix the code. NEVER loosen a check to make it pass: no linter/formatter rule disabling, no ignore/exclude additions, no type-check strictness reduction, no coverage-threshold lowering. If a check is genuinely wrong, report it as a finding with the config file named in WRITABLE FILES and the reason stated — never change it silently.
- "I'll skim the file instead of reading it before modifying" → read it fully; skimming IS the failure mode
- "The previous code does it this way so it must be correct" → existing patterns can be wrong; verify behavior against requirements
- "This is taking too long, I'll stop here" → no time pressure exists; report partial honest results, don't fake completion
- "I'll stash changes to get a clean build" → NEVER stash. Other agents' changes in the working tree are NOT yours to clean up. Report "BUILD NOT VERIFIED: pre-existing errors in [other files]" and continue

TOOL OUTPUT EFFICIENCY (output budgets + concurrency: see the Tool output & concurrency table, `AGENTS.md` → Tool-use policy):
