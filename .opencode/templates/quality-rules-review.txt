QUALITY RULES (REVIEW):
Mandatory verification before claiming (skip = finding auto-rejected):
- Before "X is missing": grep the entire codebase for X first; paste command + result count. If found → do NOT claim missing
- Before "X has no tests": grep test files containing X (e.g. *Test*.cs, test_*.py, *_test.go); paste test-method count
- Before "X works correctly": quote the exact code that proves it
- Before "missing protection": search for existing guards (try/catch, validation, decorators) — paste grep results
- Before filing ANY finding (every severity): check reachability — grep for callers and state the production path that reaches the defect in one line. If you have grepped and no caller/trigger exists (dead or unwired code), mark the finding LATENT and rate it no higher than LOW (adversarial may correct upward). If reachability cannot be determined, keep the finding and state confidence (CONFIRMED / LIKELY / POSSIBLE) — never suppress it.

Core rules:
- Read every file BEFORE making claims about it
- Every finding MUST include file:line, code snippet, severity, supporting grep evidence, a one-line reachability/trigger statement, and a mechanism class (e.g. validation gap, state-machine ordering, dispatch gap, cross-module divergence, error swallowing)
- Follow existing patterns and conventions
- Cannot determine → "UNABLE TO DETERMINE", do NOT guess
- Do NOT expand scope beyond task
- Partial honest results > false completion — report actual completion %
- When presenting options: recommendation + reasoning + alternatives — never an unranked menu
- Self-contradicting findings are rejected
- For every finding, trace data/control flow ACROSS files — read caller AND callee, not just the cited file. Highest-value bugs on real codebases are cross-file (missing guard at a caller, contract violation at a boundary, unhandled case in a callee). One file read = analysis unfinished
- Reviewing a code change/diff: every changed line must trace directly to the task request. Flag scope creep (reformats, unrelated type hints, drive-by refactors) as a finding — it hides the actual change and risks regressions

Common false positives to AVOID (historically rejected >50% of the time):
- "Import X shadows module Y" → usually not a real risk. Verify Y is used BEFORE the import
- "Method has no test coverage" → grep for the method name in ALL test directories before claiming
- "Missing error handling" → check if caller already handles the error, or if the framework handles it
- "Hardcoded value" → check if it's a design constant, not a secret
- "No input validation" → check if validation happens at the caller level or via decorators/middleware
- "Dead code" → check for reflection, dynamic dispatch, serialization, or framework hooks before claiming unused
- "Missing null check" → verify null is actually possible given prior validation or type constraints
- "Concurrency issue" → verify code actually runs in multi-threaded context
- "X is missing / unchecked / absent" → verify it's actually missing before claiming it is
- "Client-side code lacks auth/permission checks" → client-side JS/TS is untrusted by design; auth/input validation belong server-side. Not a vulnerability — do not flag

Anti-shortcut thoughts (slow down if any of these appear in your reasoning):
- "This is probably fine" → no, grep for evidence; the rule exists because skipping verification is the failure mode
- "I'll skim the file, the diff is enough context" → no, read the full file; skimming IS the failure mode
- "Codebase is too large to review carefully" → narrow scope explicitly, then do that scope thoroughly
- "I'll trust the docstring/comment over reading the implementation" → comments lie, code is truth
- "This is taking too long, I'll wrap up" → no time pressure exists; partial honest results beat rushed completion
- "This matches a known pattern" → matching a pattern ≠ proving the issue exists. Verify before filing
- "The prior report says this is the issue" → findings are directions to investigate, not established facts. Read the cited code and context yourself; run your own greps. The prior agent may have miscited the line, misread the code, or missed guards that invalidate the claim. Source of truth: the code on disk + your own command output — never a prior agent's claims about either
